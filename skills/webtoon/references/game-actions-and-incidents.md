# ゲーム操作・装備・得意分野・大事件をつなぐ

VRMMORPGを実際に遊ぶ話、装備の働きが分からない話、主人公の得意分野が見えない話、穏やかな展開に大事件を加える改稿で読む。『塔を灯す剣』で受けた指摘から、別作品にも使える判断を整理する。ゲームが現実へ変わる話、特定の剣や塔、同じ消費量を新作の既定にしない。

## 操作が行動を変えるところへゲーム窓を置く

ゲームであることを導入の説明だけへ任せず、必要な場面でステータス、装備詳細、試験ログ、招待、参加、イベント通知などを使う。全コマへ窓を置くのではなく、見る・押す・閉じることで人物の判断や行動が変わる箇所を選ぶ。

手や視線の入力動作と、窓の所有者、誰に見える情報か、正確な行を記録する。本人だけが見るHUDを他人が当然のように読む構図へしない。仲間は結果の観察や短い発話から共有する。操作音と自動着信の音を区別し、通知を読んだことと本人が事件を起こしたことを混同しない。

UIは今回のゲームに合う機能的な形へ整える。会話を縦書きにする既定を、数値やHUDの行へ無条件で適用しない。窓の光学表現は[システム表示](system-and-lettering.md)、発話と音の独立指定は[作画指示](art-prompts.md)を参照する。

## 武器の正体・働き・止まり方を先につなぐ

| 確認すること | 読者へ見せる証拠 |
| --- | --- |
| 何の武器か、誰が作り誰が持つか | 名前、返却や受け渡し、同じ意匠と手の状態 |
| 普通の武器と何が違うか | 発動する瞬間と、その結果。必要なら短い装備表示 |
| 消費や発熱が何を意味するか | 作動、失敗、ログ、部品の観察を順につなぐ |
| 止まると何が失われるか | 強化だけが止まるのか、武器そのものが使えないのかを描き分ける |

『塔を灯す剣』では普通の鋼剣に斬撃強化を加え、変換損失で熱が残り、安全停止で強化だけが止まる。炎で敵を焼く武器にはしない。作者の説明、ゲーム表示、刃の光、人物の発話が同じ機能を示すように揃えた。この機構と数値は作品固有の例で、全ての魔法武器へ適用しない。

残量、出力停止、排熱の詰まり、回路破損は別の状態として管理する。ログが示す事実と、人物が観察して判断する原因も分け、見つける前に正解を通知へ全部書かない。

## 得意分野は比較と選択の結果で示す

能力値や称号だけで「秀でている」と説明せず、本人の観察・設計・試行が何を良くしたか見せる。同じ威力で消費を抑える、制約の中で仲間の道具を改善するなど、比較対象と結果が読める場面を選ぶ。

既に得意な技術と、これから覚える剣術などは両立できる。後続話で主人公を基本操作も知らない初心者へ戻さず、未知の部品、長時間の使用、現地の制約、仲間との連携へ課題を移す。万能化や急な隠し能力を足すことを、得意分野の証明に代えない。

## 大事件は、理解と感情を保って世界の尺度を変える

展開が穏やかすぎるという指摘では、大きな出来事を候補に入れる。前の成功や誘いを受け止めた後で、手掛かり、本人の知覚、異変の姿、暮らしや目的への影響、次の行動の選択をつなぐ。原因、組織名、期限、報酬まで一度に読ませる必要があるかを判断する。

『塔を灯す剣』では二人の約束の後、灯具の明滅と振動、上を見る目、塔の巨大な光環、東門と工房街の停止、通知を読んで戻る選択へ進む。原因と回収条件は次話に残す。大きな姿の前へ音と視線を渡す演出は[コマと余白を跨ぐ音](cross-panel-sounds.md)を参照する。音の演出はユーザー採用済みだが、この事例全体の読者理解や全話の完成承認は未確認。

作者側では事件の原因と影響範囲、復旧条件、通れる経路、翌話の時間と装備を先に整合させる。閉じた門から次話で入る、停電の翌日に説明なしで元通りなどを避け、使う入口や時間の切り替わりを絵と必要な接続文で示す。

「技術的にもできそう」を求められたゲームなら、何でも自由に書き換える力を安易に追加せず、状態・入力・資源・部品の組合せと遷移から作動を設計する。作者が把握する実装の仕組みと、人物が今知ることを分ける。実際に遊ぶゲームという前提へ、ログアウト不能や現実の死などを無断で追加しない。
