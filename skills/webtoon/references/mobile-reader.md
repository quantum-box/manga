# HTMLで仕上げるとき

## 作画と組版を保存する

標準ではセリフと吹き出しを含めた原画を `art/`、場面の順序・幅・余白を `index.html`、必要なら `reader.css` に保存する。各場面を `<figure class="scene">` とし、画像を幅100%、高さ自動で置く。先に[余白とスクロール](scroll-pacing.md)の設計を組版へ移し、必要な間を独立した区間として置く。画像を順に積むだけで仕上げとしない。既に画像に含まれる文字をHTMLでも重ねない。`storyboard.md` に全文と話者を残し、画像の `alt` にもセリフを含める。

この方式で編集できるのはHTMLの組版であり、原画内の文字は画像生成で編集する。文字の個別編集を指定された場合は、文字と吹き出しをHTMLの別要素として置く方式を使う。日本語のセリフには `writing-mode:vertical-rl` を使い、列の長さと吹き出しの形を調整する。ナレーション・音・看板は場面に合う方式を選ぶ。

[reader.css](../assets/reader.css) は基本の組版だけを提供する。コピーしてから色、字形、余白、吹き出し、画像端のつなぎ方を物語へ合わせる。画像枚数や見せ順は含んでいない。

```html
<main class="episode">
  <figure class="scene" id="descent">
    <img src="art/descent.png" width="724" height="2172" alt="視点が下へ移る場面。人物『誰かいる？』。セリフは縦書きの吹き出しとして画像に含まれる">
    <p class="sound" id="cue" style="top:21%;right:14%;writing-mode:vertical-rl">ちりん</p>
  </figure>
  <div class="pause" style="--pause:clamp(240px,90cqw,440px)"
       data-pacing-purpose="音の発生源を探して待つ" aria-hidden="true"></div>
  <figure class="scene" id="answer">
    <img src="art/answer.png" width="1122" height="1402" alt="音の発生源が現れる">
  </figure>
</main>
```

寸法・余白の長さ・文字は例。画像の実際の寸法を指定し、間の長さは確認した画面高と通読で調整する。全画像間にこの長さを適用しない。例の効果音は、画像にまだ含まれていない場合だけ別要素にする。HTML文字には横幅に応じた `cqw` を使える。縦書きの効果音に `cqi` を使うと意図した幅基準から変わることがあるため、実測する。

余白の区間は、何も描かない間、効果音だけ、セリフ・心の声だけ、光や影などの視覚演出だけにも使える。文字を原画に含める方式では、その要素だけの疎な原画を使う。HTMLで文字を組む方式を選んだ場合は、既存画像に同じ言葉がない区間へ置く。次はセリフだけの余白の組版例であり、長さや位置の固定値ではない。

```html
<div class="pause" style="--pause:clamp(360px,140cqw,680px)"
     data-pacing-purpose="姿のない声を聞いて返事を待つ">
  <p class="line" style="position:absolute;top:25%;right:42%;writing-mode:vertical-rl">……聞こえる？</p>
</div>
```

意味のあるセリフを含む区間全体へ `aria-hidden="true"` を付けない。話者・発話か心の声か・読む順は前後の場面と絵コンテでつなぐ。声の表現に応じて枠なしや吹き出しを選び、人物や尾を毎回追加することを要求しない。語句、濃淡、位置が変わった場合は読みやすさと次の情報までの距離を測り直す。

## 画像内のセリフを確認する

読める字の大きさと、内容を追える速度は別に確認する。連続してスクロールし、今の場所・人物の位置・何に反応したか・次の行動の理由を直前の絵から説明できるかを見る。会話を分けた場合は、話者や接写が変わっても同じ場面だと分かり、重要な説明と返答の間に受け止める時間があるかを確かめる。全員を毎コマ描く必要はない。[実例と確認項目](context-and-dialogue.md)を使い、コマ数や全長だけで判定しない。

コマの大小を変えた場合は、小さいコマでも対象が分かり、狭くした会話コマの字が読めるか確認する。大コマの焦点が埋もれていないか、左右の配置や枠なしの場面でも上から下への読順が続くかを、隣のコマと一緒に見る。

CSSの `font-size` とDOMの文字は画像内の字を測れない。390pxと360pxの実際の表示幅で書き出した画像を見て、全文・誤字・句読点、縦列が上から下／右から左に読めること、吹き出しの読む順と話者、顔を隠さないことを確認する。画像の読み込み成功だけを文字の確認結果としない。

字の表示高さの目安は `原画の字の高さ × コマの表示幅 ÷ 原画の幅`。たとえば1024px幅の原画の60pxの字を360px幅で表示すると約21px。原画内の字の大きさを実測していない場合は、計算値を実測した最小フォントサイズとして報告しない。字が小さいときは、その原画の文字と吹き出しを拡大する編集を行い、人物・背景・セリフ全文を維持する。

輪郭、内側の余白、改行も両幅で見る。大きい幅で自然でも、360pxでは語尾の一文字だけが次行へ落ちることがある。文意の区切りで改行し、文言を変えていないことを確認する。生成した称号・効果音・システム通知は[専用の判断基準](system-and-lettering.md)で、読みやすさと作中の見え方を一緒に確認する。

`validation.json` にはHTML文字の検査と画像内の文字の目視確認を区別して記録する。話者ごとの全文、列順、確認した表示幅、修正した原画を追えるようにする。

## 見せ順の測定

作品が「問いを見せてから答えを隠して待たせる」と決めた箇所だけ、先に見る要素の下端と、答えが見え始める位置の距離を確認する。二つの場面の上端だけを比べない。

たとえば問いの下端が3150px、答えの始まりが4010pxなら距離は860px。表示高844pxでは同時に見えない。別の端末の表示高が長ければ同時に見えることがあるため、確認した範囲だけを報告する。背景や視線をたどる間と、無言の余白で待つ間のどちらが合うかを選ぶ。音や問いを先に出し、そのあと広い余白を読む構成も使える。

距離の条件を満たしたあと、実際に読んで待つ時間を確認する。同時に見えないことと、発見への期待や余韻を感じることは別の確認事項。必要なら距離を表示高で割った画面数も記録する。具体的な調整は[間とスクロールの実例](scroll-pacing.md)を参照する。

UIを操作するブラウザツールのドキュメントを読み、スクロールと観察はそのツールで行う。DOMの読み取りが利用できる場合の確認例:

```javascript
() => {
  const cue = document.querySelector('#cue').getBoundingClientRect();
  const answer = document.querySelector('#answer').getBoundingClientRect();
  return {
    width: innerWidth,
    height: innerHeight,
    pageWidth: document.documentElement.scrollWidth,
    imagesLoaded: [...document.images].every(i => i.complete && i.naturalWidth > 0),
    revealDistance: answer.top - cue.bottom,
    fonts: [...document.querySelectorAll('.line,.bubble')]
      .map(e => getComputedStyle(e).fontSize)
  };
}
```

距離はDOMの画面内座標同士ならスクロール位置によらない。文字や小道具を隠す `overflow:hidden` で問題をごまかさず、要素の左右端と見た目も確認する。すべての場面が別画面になることを要求しない。

表示を読み直した直後は、HTMLの解析途中で画像数が少なく、見えている画像だけが読み込み済みという状態があり得る。ページの読み込み完了を待ち、完成本文の想定画像数と実数も照合してから測る。原画の種類数、切り出した表示窓の数、DOMの画像数は別々に記録する。同じ原画を複数窓で使う場合は数字が一致しない。

## 包装と書き出し

`scripts/package_reader.py` はローカルの `<img src="…">` と `<link rel="stylesheet" href="…">` をHTMLへ埋め込む。画像バイトは変更しない。入力ディレクトリ内のPNG/JPEG/WebP/GIF/AVIF、画像を参照しないCSSを対象にする。ネット上の資源やCSSの `url()` / `@import` は取得しないため、この小さな漫画リーダーでは外部依存を使わない。

包装後の `reader.html` を実際に開き、画像と文字が表示されることを確認する。ブラウザが作業後も残せるなら、完成した読書画面を成果物として残す。

完成画像は文字組み後のブラウザ全体をキャプチャする。スクロールして読むための画像なので、長い出力を一画面へ縮小して品質判断しない。ブラウザの拡大率や端末倍率が設定と違う場合は、CSSの表示範囲と保存画像のピクセル寸法を別々に確認する。現在のブラウザで問題がなければ補正を固定値で入れない。

ブラウザ設定とCSS表示範囲が一致しない場合は、現在の倍率を測り、スクリーンショットの座標・幅・高さもそのツールの仕様に合わせる。今回の実例では80%が残り、設定312×675が実際の390×844 CSS pxに対応した。これは環境の観測値であり、次回の設定値ではない。保存画像の寸法で補正結果を確認し、DOM全長と完成画像に1pxの丸め差があればその差を記録する。

一時的なviewport指定は確認後に戻す。成果物として残すタブは、使用中のブラウザツールが提供する保持方法で残す。報告に添える画面は、修正した表示だけでなく、前後の絵やセリフを含めて選ぶ。

## 修正した版をすべての出力へ反映する

採用版の原画・生成文字の参照を変更したら、編集元HTML、単独リーダー、完成画像を順に再出力する。前版はGitの履歴で管理し、採用版に必要な原画・参照素材だけを残す。表情だけ、表示だけの修正なら、物語の全文と見せ順が意図せず変わっていないかを照合する。

既存の作品カタログやアプリ同梱版を持つプロジェクトでは、そのプロジェクトの同期方法で採用版を更新し、照合する。今回の `manga` プロジェクトには `scripts/sync_ios_webtoons.py` と `--check` があった。別の作業場所で同じスクリプトがあるとは仮定しない。

保存先・カタログ・同梱リーダーの一致を確認したことと、iOS実機・TestFlight・公開サイトの確認を分ける。画像や組版だけの変更を理由に、無関係な重いビルドや全テストを追加しない。変更に関係する同期チェック、原本・文言の照合、表示確認を行う。

## 同じ原画を複数の表示窓へ使う場合

同じPNGの別の範囲を順に見せる場合、単体HTMLへ原画を一度だけ埋め込み、各窓へ描画する方式も選べる。原画プールからCanvasへ描く実装なら、プールの全原画を読書画面へ表示して後の出来事を先出ししない。これは配布サイズと描画の選択肢であり、Canvasを必須にする指示ではない。

- 原画数、表示窓数、DOM画像数を分ける。元PNG座標の切り出し、表示幅、左右位置、次までの間を記録する。各窓の代替テキストはそこで読める内容に絞り、後の答えを説明しない。
- 画像の読み込み・decodeと全窓の描画完了を待ってから完成画像を保存する。原画プールを描画後に解放する方式では、`document.images` がゼロでも未描画とは限らない。窓の完了状態を検査し、画像取得やdecodeの失敗を読者へ表示する。JavaScriptが必要な方式では、その依存も明示する。
- Canvasの整数の画素寸法と、CSSの正確な縦横比を区別する。窓ごとの丸めで全編の位置がずれないよう、ネイティブ書き出しと同じ連続した配置を使う。全原画を重複保持したり、必要以上に高解像度のCanvasを全窓へ作ったりしない。
- DOMアダプタで実行したスクリプト検査は、参照、描画呼び出し、失敗時の動作を確かめる。CSSの実寸、ブラウザ画面、スクロールでの読み心地、実機の証明とは分ける。ネイティブ書き出しの確認もブラウザ確認として報告しない。

切り出し境界では、次のコマの枠線やフェードまで見る。書き出した画像・単体HTML・ZIPの実サイズを記録し、投稿や公開を行う場合は投稿先の最新制限に合わせる。検査できない環境ではネイティブ画像と参照照合を進め、ブラウザ・実機確認は未実施のまま記録する。旧版の確認結果を改稿版の確認結果として引き継がない。[全編改稿の制作例](scroll-revision-lessons.md)を参照する。
